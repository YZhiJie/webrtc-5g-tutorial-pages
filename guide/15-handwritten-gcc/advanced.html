15.2 进阶应用：延迟梯度、卡尔曼滤波与状态机 ​

GCC 的精妙之处在于：它不把「延迟高」当拥塞，而是把「延迟在变大」当拥塞。这一章我们拆开它的四个核心组件，看它们如何协同工作。

15.2.1 Arrival-time Filter：分组到达间隔 vs 发送间隔 ​

GCC 的输入不是单个包的延迟，而是两组包之间的相对关系。

发送端                          接收端
  │                               │
  │  T1: 发出包组 A (1000 bytes)  │
  │ ────────────────────────────> │  A1: 到达
  │                               │
  │  T2: 发出包组 B (1000 bytes)  │
  │ ────────────────────────────> │  A2: 到达
  │                               │

定义两个时间差：

符号含义公式
send_delta两组包的发送间隔T2 - T1
arrival_delta两组包的到达间隔A2 - A1

如果网络空闲，接收端应该原样复制发送端的时间模式：

send_delta ≈ arrival_delta   →   一切正常

如果网络拥塞，包在路由器里排队，后到的包要等前面的包发完：

arrival_delta > send_delta   →   队列在堆积

15.2.2 Delay Gradient：延迟梯度的定义 ​

延迟梯度（Delay Gradient） 就是两者的差值：

delay_gradient = arrival_delta - send_delta
场景delay_gradient含义
队列稳定≈ 0延迟不变，链路刚好跑满
队列变长> 0延迟在增加，即将拥塞
队列变短< 0延迟在减小，链路易空闲

注意 GCC 关注的是变化趋势而不是绝对值：

  • 延迟 200ms 但稳定 → 不一定拥塞（可能是跨洲链路）
  • 延迟 20ms 但每秒涨 10ms → 即将拥塞

15.2.3 Trendline Filter：用线性回归平滑梯度 ​

原始 delay gradient 非常 noisy（有抖动、有乱序），不能直接用来调码率。GCC 用最小二乘线性回归（Least Squares Linear Regression） 拟合最近 N 个样本的趋势。

算法 ​

对最近 20 个样本 (x_i, y_i)，其中 x_i 是时间，y_i 是 delay gradient，拟合直线：

y = a + b·x

最小化误差平方和：

min Σ (y_i - a - b·x_i)²

解得斜率：

        n·Σ(x_i·y_i) - Σx_i·Σy_i
b = ─────────────────────────────
        n·Σx_i² - (Σx_i)²

为什么是斜率而不是均值？ ​

样本值
  ↑
  │    ●
  │   ● ●        ●
  │  ●   ●      ● ●
  │ ●     ●    ●   ●
  │        ●  ●     ●
  │         ●        ●
  └────────────────────→ 时间
         ↑
    斜率 b > 0：虽然当前值不高，但趋势在涨
  • 均值告诉你「现在延迟高不高」
  • 斜率告诉你「延迟在变好还是变坏」

GCC 要的是预测，所以用斜率。

15.2.4 Overuse Detector：阈值自适应与状态机 ​

得到 trendline 斜率后，Overuse Detector 判断当前链路状态。

三态状态机 ​

         ┌─────────┐
         │  Normal │
         └────┬────┘
              │ slope > threshold 持续一段时间
              ▼
         ┌─────────┐
    ┌───│ Overuse │◄──┐
    │    └────┬────┘   │
    │         │ slope < -threshold
    │         ▼        │
    │    ┌─────────┐   │
    └───│ Underuse│───┘
         └─────────┘
状态含义控制器动作
Normal链路刚好跑满保持或微调
Overuse队列在堆积乘性减少码率
Underuse队列在排空加性增加码率

阈值自适应（Adaptive Threshold） ​

固定阈值的问题：

  • 阈值太小 → 一点抖动就误报 overuse
  • 阈值太大 → 真拥塞了检测不出来

GCC 的解法是让阈值自己动：

if |slope| > threshold:
    threshold += K · |slope| · Δt    # 放宽
else:
    threshold -= K · |slope| · Δt    # 收紧

这样当网络抖动大时，阈值自动放宽；网络稳定时，阈值自动收紧。

15.2.5 AIMD Controller：加性增 / 乘性减 ​

这是 TCP 的经典策略，GCC 在延迟域做了同样的事。

码率
  ↑
  │      /\
  │     /  \
  │    /    \        ← Overuse 触发
  │   /      \      /
  │  /        \    /
  │ /          \  /
  │/            \/
  └────────────────→ 时间
    加性增加   乘性减少
    (慢)      (快)
状态动作公式为什么
Underuse / Normal加性增加R += step慢慢试探，别冲过头
Overuse乘性减少R *= factor快速刹车，防止雪崩

典型参数（WebRTC 默认）：

  • 加性步长：+5 ~ +50 kbps（每次反馈）
  • 乘性因子：0.85（砍 15%）
  • 最小码率：100 kbps（保证基本通话）
  • 最大码率：5 Mbps（受限于编码器能力）

15.2.6 目标码率收敛与边界 ​

AIMD 的收敛过程：

码率
  ↑
  │                                    ╭──── 最大码率(5 Mbps)
  │                                   /
  │                  ╭──╮            /
  │                 /    \          /
  │        ╭──╮    /      \    ╭───╯
  │       /    \  /        \  /
  │  ╭───╯      \/          \/
  │  /
  │ /
  └────────────────────────────────→ 时间
    ↑        ↑        ↑        ↑
  初始    Overuse   收敛    容量变化
  探测    急刹车    稳定    重新收敛

边界处理：

  • 撞下限：低于 100 kbps 时不再降（否则画面全黑）
  • 撞上限：高于 5 Mbps 时不再加（编码器编不动）

15.2.7 卡尔曼滤波在原始 GCC 中的角色 ​

2012 年的原始 GCC 论文用的不是 Trendline Filter，而是卡尔曼滤波（Kalman Filter）。

卡尔曼滤波版本 ​

把延迟梯度建模为一个线性系统：

状态方程：  x_k = x_{k-1} + w      (w 是过程噪声)
观测方程：  z_k = x_k + v          (v 是观测噪声)

通过递归的「预测-更新」循环，估计出最优的当前梯度值。

为什么被 Trendline 取代？ ​

维度卡尔曼滤波Trendline Filter
计算复杂度高（矩阵运算）低（纯标量）
参数调优难（Q/R 矩阵）简单（窗口大小）
对突发响应慢（惯性大）快（窗口滑动）
可解释性黑盒白盒（线性回归）

2016 年后，WebRTC 全面切换到 Trendline Filter。卡尔曼滤波作为历史背景了解即可。

15.2.8 小结 ​

输入: 包到达时间
  ↓
Arrival-time Filter  →  计算 delay_gradient = arrival_delta - send_delta
  ↓
Trendline Filter     →  最小二乘回归，输出斜率 slope
  ↓
Overuse Detector     →  阈值比较 + 状态机，输出 Normal/Overuse/Underuse
  ↓
AIMD Controller      →  加性增 / 乘性减，输出目标码率
  ↓
编码器                →  按目标码率编码视频

四个组件各司其职，共同完成「在延迟爆炸前踩刹车」的任务。
