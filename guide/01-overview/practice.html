1.3 实战案例：5G 场景下 WebRTC 的优势定位 ​

把 WebRTC + 5G 组合的优势落到具体业务场景，建立"什么时候用 WebRTC、什么时候用 RTMP"的决策直觉。

1.3.1 场景决策矩阵 ​

场景实时性要求并发量推荐方案原因
电商直播（带货）低（5~30 秒可接受）高（10w+）WebRTC + SFU 或 RTMP需要时切换互动
直播连麦 PK高（< 300ms）中（1w+）WebRTC + SFURTMP 做不到低延迟互动
在线教育互动高（< 200ms）中（5k+）WebRTC + SFU + MCU需要多路合流录制
云游戏 / 云桌面极高（< 100ms）低~中WebRTC + 专用编码器端到端必须低延迟
竞技直播（电竞赛事）高（< 300ms）高WebRTC + SFU + 5G MEC低延迟 + 边缘分发
企业视频会议高低~中WebRTC MCU多路混音
安防监控中高WebRTC 拉流浏览器原生支持，无需插件
远程医疗极高（< 50ms）低WebRTC + 5G URLLC医疗级时延要求

核心判断标准：是否需要互动（双工或多向）。需要互动 → WebRTC；纯播放 → RTMP/HLS/DASH。

1.3.2 5G + WebRTC 直播延迟预算 ​

完整分解一帧画面在 5G 网络下的端到端延迟：

采集 ──► 编码 ──► 传输 ──► 转发 ──► 传输 ──► 解码 ──► 渲染
│       │        │       │       │       │       │
│~1ms   │5~15ms  │3~10ms │5~20ms │3~10ms  │5~15ms │~5ms
└──────────────────────────────────────────────────┘
                    总计 ≈ 30~70ms（5G 下）

对比 4G + RTMP：

采集 ──► 编码 ──► RTMP ──► CDN ──► HLS ──► 解码 ──► 渲染
│       │        │        │       │       │       │
│~1ms   │10~30ms │300ms   │100ms  │1000ms  │10~30ms│200ms
└──────────────────────────────────────────────────┘
                    总计 ≈ 1.6~2.0 秒

关键差距：WebRTC 不做 GOP 缓存，直接逐帧传输。5G 把传输延迟进一步压低到两位数毫秒。

1.3.4 下一阶段路线图 ​

基于 WebRTC + 5G 能力，你的产品可以按以下路线演进：

阶段 1 · 基础能力（第 2~5 章）
  ├─ 摄像头采集 + PeerConnection 一对一通话
  └─ WebSocket 信令 + Coturn TURN

阶段 2 · 多人直播（第 7~8 章）
  ├─ Mediasoup / Janus SFU 部署
  ├─ 多房间 + 多人连麦
  └─ WebRTC → RTMP 转推（兼容传统 CDN）

阶段 3 · 5G 优化（第 6、9 章）
  ├─ 5G MEC 边缘 SFU 部署
  ├─ 基于 QFI 的 QoS 调度
  ├─ 移动端智能码率切换
  └─ NWDAF 网络数据分析

阶段 4 · 生产落地（第 10 章）
  ├─ 全链路监控（质量数据 + 网络数据）
  ├─ 弱网降级策略（自动切 RTMP）
  └─ 合规（加密、隐私、数据主权）

小结 ​

你应该记住
WebRTC 是什么浏览器内置的实时通信栈，三件套：getUserMedia + PeerConnection + DataChannel
5G 怎么帮 WebRTCeMBB（大上行带宽）、URLLC（空口 < 10ms）、MEC（边缘部署）、切片（QoS 保障）
何时用 WebRTC需要互动（多向实时）的场景。纯播放用 RTMP/HLS。
5G 也有坑IPv6-only、网络抖动、电量消耗——需要针对性处理
