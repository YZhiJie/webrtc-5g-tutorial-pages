12.1 基础入门：中继、分配与租约 ​

当对称 NAT（Symmetric NAT）让 STUN 反射地址彻底失效时，只剩一条路：让一台有公网 IP 的服务器替你"代收代发"。这就是 TURN（Traversal Using Relays around NAT，RFC 5766）。本模块我们将不用任何第三方库，纯手写一个 mini TURN 服务器——先把六个核心方法与一次完整的分配事务讲清楚。

12.1.1 为什么 STUN 会失败：对称 NAT ​

回忆模块四：STUN 能告诉你"你的公网映射地址（srflx）是什么"。但这个地址有个前提——NAT 的映射必须对所有目的地保持一致。

对称 NAT 恰好打破了这个前提：每换一个目的地址，NAT 就换一个新的映射端口。

  客户端 192.168.1.2:5000
    │
    ├─ 发包给 STUN 服务器 A  ──► NAT 映射为  114.5.5.5:60001   ← STUN 告诉你这个地址
    │
    └─ 发包给对端 B         ──► NAT 映射为  114.5.5.5:60002   ← 对端连 60001，根本到不了你！

5G 网络的残酷现实：运营商的 CGN（Carrier-Grade NAT，运营商级 NAT）几乎都是对称 NAT。这意味着在 5G 场景下，TURN 不是可选项，而是兜底刚需。

TURN 的思路很直接——既然你们互相够不着，那就都在一台公网服务器上"开个窗口"，所有流量都经过这个窗口中转：

  客户端 A                                        对端 B
     │                                               │
     │  ① Allocate：在 TURN 上申请一个中继端口        │
     ▼                                               │
  ┌────────────────────────┐                         │
  │     TURN 服务器         │                         │
  │  127.0.0.1:3478 (控制口) │                         │
  │  中继口 relayed address  │ ◄──── B 直接发 UDP ─────┘
  │  例如 9.9.9.9:52297     │
  └────────────────────────┘
     ▲
     └── B 发给 relayed address 的包，被 TURN 包装后转给 A

代价也很直接：所有媒体流量都要经过 TURN 服务器进出两次，带宽成本高、延迟略增。所以 ICE 永远把 relay 候选排在最后，只在直连和 STUN 都失败时才用。

12.1.2 核心概念：分配（Allocation） ​

TURN 的一切从一次 Allocate（分配） 开始：

概念含义
分配（Allocation）客户端在 TURN 服务器上申请到的一个"中继席位"，内含一个 relayed address
中继地址（relayed address）服务器为这个分配专门开的 UDP 端口，对端把数据发到这里
控制连接客户端与 TURN 服务器之间的 STUN/TURN 通道（默认 3478 端口）
对端（peer）真正要和客户端通信的远端
  客户端 ──── STUN/TURN 消息 ────► TURN 控制口 :3478
                                     │
                                     │ Allocate 成功后，服务器新开端口
                                     ▼
  对端   ──── 裸 UDP 数据 ───────► relayed address（如 :52297）

注意：对端从来不需要懂 TURN 协议。它只要把 UDP 包发到 relayed address，TURN 服务器负责包装转发。

12.1.3 六个核心方法 ​

TURN 消息复用 STUN 的报文格式（20 字节头 + TLV 属性），核心方法只有六个：

方法方法号类别方向作用
Allocate0x003request/responseclient → server申请分配，拿到 relayed address
Refresh0x004request/responseclient → server续租；LIFETIME=0 表示主动释放
CreatePermission0x008request/responseclient → server授权某个 peer IP 可以向我转发数据
Send indication0x006indicationclient → server"帮我把这段数据发给 peer"
Data indication0x007indicationserver → client"peer 发来了这段数据"
ChannelBind0x009request/responseclient → server绑定一个 16-bit 通道号给 peer，之后走轻量 ChannelData

indication（指示）与 request 的区别：indication 没有响应，是单向通知。

还有一个特殊的 ChannelData：它不是 STUN 消息，只是 4 字节头 + 裸数据，靠高两位 01 与 STUN 消息（高两位 00）区分。详见 12.2。

12.1.4 一次完整的 Allocate 事务 ​

TURN 采用长期凭证机制（Long-Term Credential）：第一次请求故意不带凭证，服务器回 401 Unauthorized 并给出 REALM（域）和 NONCE（随机数），客户端用这些信息算出摘要后重发。密码本身永远不上网。

  客户端                                         TURN 服务器
    │                                                │
    │ ── Allocate request ──────────────────────────►│
    │    （无凭证）                                   │
    │                                                │
    │ ◄── 401 Unauthorized ──────────────────────────│
    │     REALM="mini-turn", NONCE="c421d5cf..."     │
    │                                                │
    │    key = MD5(username:realm:password)          │  ← 客户端本地计算
    │                                                │
    │ ── Allocate request ──────────────────────────►│
    │    USERNAME, REALM, NONCE                      │
    │    MESSAGE-INTEGRITY = HMAC-SHA1(key, 报文)     │  ← 服务器校验
    │                                                │
    │ ◄── Allocate success ──────────────────────────│
    │     XOR-RELAYED-ADDRESS = 9.9.9.9:52297  ★     │
    │     LIFETIME = 600                             │
    │                                                │

拿到 XOR-RELAYED-ADDRESS（异或中继地址）后，客户端就可以把它作为一个 ICE relay 候选交给对端了。地址和端口与魔数（Magic Cookie）0x2112A442 做了异或——防止途中的 NAT 设备"自作聪明"改写载荷里的明文地址。

12.1.5 租约与权限的生命周期 ​

TURN 服务器上的每样东西都会过期——这是为了回收死掉的客户端占用的资源：

资源默认时长续期方式到期后果
分配（Allocation）600 秒Refresh 请求relayed address 回收，全部权限/通道失效
权限（Permission）300 秒（5 分钟）重发 CreatePermission该 peer IP 的入站数据被丢弃
通道绑定（Channel Binding）600 秒（10 分钟）重发 ChannelBind回退到 Data indication 方式

两个容易记混的点：

  1. Refresh 的 LIFETIME=0 是"主动释放"，不是"续 0 秒"——服务器立刻回收分配。优雅下线要用它，否则服务器要等 600 秒才能回收资源。
  2. 权限只有 5 分钟而分配有 10 分钟——通话超过 5 分钟时，千万别忘了重发 CreatePermission，否则会突然收不到对端数据（典型的"通话 5 分多钟必断" bug 的根源）。

12.1.6 小结 ​

你应该记住
对称 NAT 下 STUN 必败映射端口随目的地变化，srflx 地址对 peer 无效
TURN = 公网代收代发代价是带宽翻倍、延迟略增
六个方法Allocate / Refresh / CreatePermission / Send ind. / Data ind. / ChannelBind
401 质询流程无凭证 → 401（REALM+NONCE）→ 带 MESSAGE-INTEGRITY 重发 → success
600s 租约 / 300s 权限都要续；LIFETIME=0 主动释放
