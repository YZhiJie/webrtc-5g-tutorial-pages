16.1 基础入门：UDP 之上的握手与加密 ​

WebRTC 强制要求所有媒体流必须加密传输，这是写进 RFC 的硬规定（RFC 8827）。但媒体走的是 UDP，而 TLS 依赖 TCP 的可靠有序特性——于是就有了 DTLS：把 TLS 的握手和密码学原封不动搬到 UDP 上，再叠加一层 SRTP 给每个 RTP 包做加密和认证。本章讲清楚这两个协议是什么、为什么需要、以及它们如何协同。

16.1.1 为什么 UDP 上还要握手 ​

WebRTC 的安全模型有一条不可协商的红线：

┌─────────────────────────────────────────────────────┐
│  所有媒体（音频/视频）必须加密，没有"明文模式"开关      │
│  —— RFC 8827 (WebRTC Security Architecture)         │
└─────────────────────────────────────────────────────┘

为什么不能像传统直播（RTMP/HLS）那样允许明文？因为 WebRTC 是浏览器原生 API：

  • 浏览器是第三方代码运行环境，网页 JS 可以拿到媒体流
  • 如果媒体是明文，恶意网页可以悄悄把摄像头画面转发到任何服务器
  • P2P 通信跨越不可信网络（咖啡店 Wi-Fi、运营商骨干网），窃听成本极低

所以 WebRTC 规定：媒体加密使用 DTLS-SRTP，且密钥必须由通信双方直接协商（DTLS 握手），不能经过信令服务器传递。即使信令服务器被攻破，攻击者也无法解密媒体内容——这叫端到端加密（End-to-End Encryption, E2EE） 的基础形态。

但问题来了：

媒体走 UDP 的原因：
  - 低延迟（TCP 重传会卡画面）
  - 容忍丢包（丢一帧比等重传好）

TLS 不能跑在 UDP 上的原因：
  - 握手依赖可靠传输（丢一个握手包整个流程卡死）
  - 加密记录依赖有序到达（TLS 用隐式序列号计算 MAC）
  - 没有 TCP 的"连接"概念，无法防简单的源地址欺骗

解法就是 DTLS（Datagram Transport Layer Security，数据报传输层安全协议）：RFC 6347 定义，本质上就是"能跑在 UDP 上的 TLS"。

16.1.2 DTLS = TLS over UDP：解决重传与乱序 ​

DTLS 1.2 对应 TLS 1.2，DTLS 1.3 对应 TLS 1.3。它针对 UDP 的三个缺陷各打了一剂补丁：

UDP 的缺陷DTLS 的补丁机制
丢包不重传握手重传定时器每个握手消息发送后启动定时器，超时未收到对方下一条消息就重发
包乱序到达epoch + sequence number每条记录显式携带 16-bit epoch + 48-bit 序列号，接收方按序号重组
无连接、易伪造Cookie 机制（HelloVerifyRequest）服务器先验证客户端 IP 可达，再分配资源

Cookie 机制：防 DoS 的第一道门 ​

UDP 最大的安全隐患是源地址伪造（IP Spoofing）：攻击者可以用受害者的 IP 作为源地址向服务器发送 ClientHello，服务器如果直接分配状态并回复大量数据，就成了放大攻击（Amplification Attack）的帮凶。

DTLS 的应对（借鉴自 SCTP）：

客户端                                    服务器
  │                                        │
  │ ── ClientHello (无 cookie) ──────────> │
  │                                        │ 服务器不分配状态，
  │                                        │ 只生成一个 cookie
  │ <── HelloVerifyRequest (含 cookie) ─── │ (通常是 HMAC(客户端IP, 密钥))
  │                                        │ 【无状态，可丢弃】
  │                                        │
  │ ── ClientHello (带回 cookie) ────────> │ 验证 cookie 有效 → 才分配状态
  │                                        │ 证明客户端确实持有该 IP
  │ <── ServerHello ────────────────────── │
  │              ...继续完整握手...          │

关键点：HelloVerifyRequest 阶段服务器完全无状态——cookie 是用服务器私有密钥对客户端 IP 做 HMAC 算出来的，服务器不需要存任何东西，收到带回 cookie 的 ClientHello 时重新算一遍对比即可。伪造了源 IP 的攻击者收不到 cookie，自然无法完成第二步。

epoch 与 sequence number：给每条记录编号 ​

TLS 的记录层用隐式序列号（双方各自维护计数器），这要求 TCP 保证有序。DTLS 改为显式编号：

DTLS 记录头 (13 字节)：
┌──────────┬─────────┬──────────────┬──────────────────┬──────────┐
│  type    │ version │    epoch     │ sequence_number  │  length  │
│ (1 byte) │(2 bytes)│  (2 bytes)   │    (6 bytes)     │ (2 bytes)│
└──────────┴─────────┴──────────────┴──────────────────┴──────────┘
  • epoch（纪元）：每完成一次 ChangeCipherSpec（切换加密套件），epoch 加 1。epoch=0 是明文握手，epoch=1 是加密后的应用数据
  • sequence_number：每个 epoch 内从 0 开始递增的 48 位序号

有了显式编号，乱序到达的记录可以被重新排序，重复的记录可以被丢弃——可靠性由 DTLS 自己保障，不再依赖下层传输协议。

16.1.3 DTLS 握手全流程 ​

WebRTC 中 DTLS 握手的完整消息流（RFC 6347 + RFC 5763）：

客户端 (Controlling)                          服务器 (Controlled)
   │                                              │
   │ ──── 1. ClientHello ───────────────────────> │   支持套件列表、random、扩展
   │                                              │
   │ <──── 2. HelloVerifyRequest ──────────────── │   下发 cookie（防伪造）
   │                                              │
   │ ──── 3. ClientHello (含 cookie) ───────────> │   证明 IP 可达
   │                                              │
   │ <──── 4. ServerHello ─────────────────────── │   选定套件、server random
   │ <──── 5. Certificate ─────────────────────── │   自签名证书（WebRTC 不用 CA）
   │ <──── 6. ServerKeyExchange ───────────────── │   ECDHE 公钥参数
   │ <──── 7. ServerHelloDone ─────────────────── │   服务器发完了
   │                                              │
   │ ──── 8. ClientKeyExchange ─────────────────> │   客户端 ECDHE 公钥
   │ ──── 9. ChangeCipherSpec ──────────────────> │   "下一条起加密"
   │ ──── 10. Finished ─────────────────────────> │   全部握手消息的 MAC 校验
   │                                              │
   │ <──── 11. ChangeCipherSpec ───────────────── │   服务器也切加密
   │ <──── 12. Finished ───────────────────────── │   双向验证完成
   │                                              │
   │ ═══════ SRTP 加密媒体开始传输 ════════════════ │

每条消息的关键载荷：

消息核心内容作用
ClientHelloclient_random、密码套件列表、use_srtp 扩展发起协商，声明支持的 SRTP Profile
HelloVerifyRequestcookie无状态防 DoS
CertificateX.509 自签名证书提供身份公钥（配合 SDP 指纹认证，见进阶篇）
ServerKeyExchangeECDHE 服务器公钥 + 签名前向保密的密钥交换参数
ClientKeyExchangeECDHE 客户端公钥双方各自算出 pre-master secret
Finished此前所有握手消息的 verify_data（MAC）防中间人篡改握手过程

与 HTTPS 握手的两个显著不同：

  1. 证书是自签名的。WebRTC 不使用 CA 体系——浏览器为每次通话临时生成证书。身份认证不靠 CA 签名链，而是靠 SDP 中的 a=fingerprint 指纹（信令通道传递，假设信令安全）。
  2. 必须协商 use_srtp 扩展（RFC 5764）。这个扩展告诉对方："握手完成后，我们要从这次 DTLS 会话里导出 SRTP 密钥"，并声明支持的 SRTP 加密套件（如 SRTP_AES128_CM_HMAC_SHA1_80）。

16.1.4 SRTP：给每个 RTP 包上锁 ​

DTLS 握手完成后，双方并不直接用 DTLS 记录层传媒体（那样每个包要多付 DTLS 记录头开销）。而是：

DTLS 握手 ──导出密钥──> SRTP 会话密钥
                            │
RTP 包 ──> SRTP protect ──> SRTP 包 ──> UDP 发送
           (加密+认证)

SRTP（Secure Real-time Transport Protocol，安全实时传输协议），RFC 3711 定义，专为 RTP 设计的轻量级加密方案：

组件算法作用
加密AES-CM（AES Counter Mode，计数器模式）把 RTP payload 加密成密文，RTP 头保持明文（中间设备仍需读 SSRC/seq）
认证HMAC-SHA1对整个 SRTP 包（含明文头）计算认证标签，防篡改
密钥管理SRTP KDF（Key Derivation Function）从一份 master key 派生出加密密钥、认证密钥、盐值

SRTP 包的结构：

┌──────────────────┬──────────────────────┬─────────┬──────────────┐
│   RTP 头(明文)    │  加密的 RTP payload   │ MKI(可选)│  Auth Tag    │
│   12+ 字节        │   (AES-CM 密文)       │         │ HMAC-SHA1    │
│                  │                      │         │ 80 或 32 bit │
└──────────────────┴──────────────────────┴─────────┴──────────────┘
   └──────────────┬──────────────────────────────┘
                  └── HMAC-SHA1 的输入（全部认证）──┘

为什么用 AES 计数器模式（Counter Mode）而不是 CBC？

  • 随机访问：每个包用独立的计数器块加密，丢包不影响后续包解密（CBC 会连锁失败）
  • 无需填充：CTR 是流密码模式，不产生填充字节，不膨胀包大小
  • 可并行：加解密都只需要 AES 加密函数

16.1.5 密钥导出：RFC 5764 Exporter ​

DTLS 握手结束后，双方各自持有相同的 master secret。SRTP 需要的密钥材料通过 TLS Exporter 机制导出（RFC 5705 / RFC 5764）：

keying_material = TLS-Exporter(
    label  = "EXTRACTOR-dtls_srtp",   ← 固定的标识字符串
    context = "",                      ← WebRTC 中为空
    length  = 2 * (master_key_len + master_salt_len)
            = 2 * (16 + 14) = 60 字节  ← AES-128 时
)

导出的 60 字节按固定顺序切分：

字节偏移  0        16            30       46            60
         ├─────────┼──────────────┼─────────┼──────────────┤
         │ client  │   client     │ server  │   server     │
         │ master  │  master salt │ master  │ master salt  │
         │ key(16B)│    (14B)     │ key(16B)│    (14B)     │
         └─────────┴──────────────┴─────────┴──────────────┘
              └─ 客户端用它加密自己发的包 ─┘
              └─ 服务器用它加密自己发的包 ─┘

注意是双向各一份：客户端用自己的 master key/salt 加密发出的 SRTP，服务器用另一份。双方都知道两份密钥，所以都能解密对方的包，但加密方向严格分离——这避免了两个方向使用相同密钥导致的计数器冲突。

拿到 master key/salt 之后，还要经过 SRTP KDF 派生出真正干活的 session key（会话密钥），这部分细节留到进阶篇。

16.1.6 小结 ​

概念一句话
为什么强制加密WebRTC 跑在浏览器里，明文媒体=隐私灾难
DTLSTLS 的 UDP 移植版：重传定时器 + epoch/seq 编号 + cookie 防伪造
HelloVerifyRequest服务器无状态验证客户端 IP 真实性，防放大攻击
Finished对全部握手消息做 MAC，防中间人篡改协商结果
SRTPAES-CM 加密 payload + HMAC-SHA1 认证整包，RTP 头保留明文
ExporterDTLS 握手产物，label 固定为 "EXTRACTOR-dtls_srtp"，导出双向各 30 字节
