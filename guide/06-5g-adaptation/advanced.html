6.2 进阶应用：5G 切片与 QoS 保障 ​

深入 5G QoS 机制、QFI 映射、WebRTC 带宽估计与 5G 网络的联动。

6.2.1 5G QoS 模型 ​

5G 定义了更灵活的 QoS 体系：

3GPP 标准含义WebRTC 映射
5QI（5G QoS Identifier）标准化 QoS 等级WebRTC 音视频 → 5QI=37（实时，GBR）
QFI（QoS Flow Identifier）每个 QoS 流的标识WebRTC 可以携带 QFI 请求
GBR / Non-GBR保证比特率 vs 尽力而为WebRTC 音视频走 GBR，信令走 Non-GBR
ARP（Allocation and Retention Priority）资源抢占优先级WebRTC 直播设高 ARP

6.2.2 5G 切片接入点 ​

WebRTC 应用请求专用切片的三种方式：

方式适用场景实现复杂度
网络运营商标配切片与运营商合作的大型直播平台高（需企业合作）
App 直接请求支持 5G Network Exposure Function 的网络中（3GPP 正在标准化）
默认切片优化普通消费者应用低（依赖 WebRTC 自身优化）

目前大部分消费级 WebRTC 应用走"默认切片优化"——通过 WebRTC 自身的拥塞控制、带宽估计、FEC 来适应 5G。切片主要由运营商侧配置。

6.2.3 WebRTC GCC 拥塞控制 × 5G ​

WebRTC 默认用 GCC（Google Congestion Control） 做带宽估计和拥塞控制。5G 下 GCC 的表现：

5G 特性对 GCC 的影响
低时延GCC 反馈更快，带宽估计更准
高带宽GCC 不会过早降码率，充分利用 eMBB
网络切片GCC 检测到丢包减少，维持高质量
MEC SFURTT 减小，GCC 收敛更快

5G 下 GCC 默认参数可以调高：

js
// 通过 RTCRtpSender 的 setParameters 调整
const params = sender.getParameters()
params.encodings[0].minBitrate = 800_000   // 5G 下保底 800kbps
params.encodings[0].maxBitrate = 4_000_000 // 5G 下上限 4Mbps
await sender.setParameters(params)

6.2.4 5G MEC 部署实践 ​

推荐架构：

┌────────────────────────────────────────────────────────┐
│  5G 核心网                                              │
│                                                         │
│  中心机房                                        边缘机房（MEC）                        │
│  ┌──────────┐                                    ┌──────────────┐                      │
│  │ Redis    │                                    │ SFU 集群     │                      │
│  │ 信令中心 │                                    │ Mediasoup xN │                      │
│  │ 鉴权     │                                    │              │                      │
│  └────┬─────┘                                    └──────┬───────┘                      │
│       │骨干网（10~20ms）                                  │本地/区域                   │
│  ┌────┴─────┐                                    ┌──────┴───────┐                      │
│  │ CDN      │                                    │ 5G 基站集群  │                      │
│  │ 传统HLS  │                                    │ (gNodeB)     │                      │
│  └──────────┘                                    └──────────────┘                      │
└────────────────────────────────────────────────────────┘

边缘节点部署要点：

  • SFU 和 TURN 部署在同机房，Relayed 候选延迟降到最低
  • 边缘节点做热备，故障时自动切换到中心机房 SFU
  • Redis 集群跨区域同步信令状态

6.2.5 5G 也有坑 ​

坑说明应对
IPv6-only 网络部分 5G 运营商只分配 IPv6STUN/TURN 必须支持 IPv6
网络抖动高速移动下空口抖动加大增大 jitter buffer、启用 FEC
电量消耗5G 芯片组耗电是 4G 的 1.5~2×移动端降码率、GPU 硬编、屏幕关闭时停推
切片发现客户端不知道有哪些切片可用等 3GPP 标准（Rel-18+），目前运营商标配
5G/4G 切换移动中从 5G 掉到 4GICE 自动重收集，GCC 自动降码率
