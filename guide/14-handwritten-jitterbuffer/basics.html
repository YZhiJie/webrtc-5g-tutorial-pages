14.1 基础入门：抖动、乱序与播放平滑 ​

网络不是流水线。同一发端以固定间隔发出的 RTP 包，经过路由器队列、多条路径、拥塞丢包后，到达接收端时早已“面目全非”。Jitter Buffer（抖动缓冲区）就是接收端的"整形器"——把乱序的包排好队、把抖动的间隔熨平，让播放端能匀速出帧。

14.1.1 抖动（Jitter）从何而来 ​

Jitter（抖动） 是指同一数据流中相邻包的到达间隔与发送间隔之间的偏差。它不是"延迟大"，而是延迟不稳定。

三个最常见成因：

成因说明典型量级
网络队列（Queueing Delay）路由器拥塞时把包放进队列，队列长度随流量起伏，导致包与包之间的排队时间不一致10~300ms
多路径（Multipath）ECMP 或链路聚合把同一条流的包分到不同路径走，快的包先到、慢的后到0~50ms
拥塞 / 重传（Congestion / Retransmission）底层链路层重传、5G HARQ 等都会让个别包"突然晚到"50~500ms

一条看似直通的链路，在微观层面是这样的：

14.1.2 接收端时间 vs 发送端时间 ​

我们无法让接收端"看到"发送端的时钟，只能把每个包到达本地的时间与包身上携带的 RTP timestamp（发送时刻）做比较。

定义 Transit Time（传输耗时）：

transit = arrivalTime - timestamp

相邻两个包的 transit 之差，就是瞬时抖动：

D(i, i-1) = (arrival_i - timestamp_i) - (arrival_{i-1} - timestamp_{i-1})
            = (arrival_i - arrival_{i-1}) - (timestamp_i - timestamp_{i-1})
  • D > 0：这个包比上一个晚到得更多（抖动变大）
  • D < 0：这个包比上一个晚到得更少（抖动变小，甚至后来居上）

RFC 3550 建议用指数滑动平均来估算抖动 J：

J = J + (|D| - J) / 16

这是个非常实用的"记忆曲线"：突发抖动会拉高 J，但很快又会回落。

14.1.3 Jitter Buffer 的核心任务 ​

接收端把 RTP 包送进 Jitter Buffer 后，Jitter Buffer 要解决三件事：

  1. 乱序重排（Reorder）

    • 包不一定按 seq 号到达。Jitter Buffer 先把所有到达的包按 seq 存进一个有序容器（常用环形缓冲区或 Map），等播放器来取。

  2. 消除抖动（De-jitter）

    • 播放器是匀速的（比如每 20ms 取一帧），但网络不是匀速的。Jitter Buffer 用"等待"把早到的包囤起来、让晚到的包能赶上，从而把输出间隔抹平。

  3. 控制延迟（Latency Control）

    • 囤得越久，抖动吸收越好，但端到端延迟也越大。Jitter Buffer 必须在"不卡顿"和"低延迟"之间找到一个平衡点。

14.1.4 固定深度 vs 自适应深度的权衡 ​

最简单的 Jitter Buffer 是固定深度（Fixed Size）：播放器始终比最早到达的包慢 N 毫秒（如 200ms）。只要所有包在 200ms 内到达，就不会断粮。

js
// 伪代码：固定深度
const PLAYOUT_DELAY = 200; // ms
function onTick(now) {
  const target = now - PLAYOUT_DELAY;
  const frame = findFirstFrameWithTimestampLE(target);
  play(frame);
}

固定深度的缺陷：

场景问题
网络突然变稳定（抖动变小）200ms 白白浪费，延迟降不下来
网络突然恶化（抖动变大）200ms 不够，频繁断粮、卡顿

自适应深度（Adaptive Size） 的思路是：持续测量历史抖动 J，让目标延迟动态地“尾随”它。

targetDelay = clamp(baseDelay + k * J, minDelay, maxDelay)
参数典型值含义
baseDelay20~50ms留给解码和渲染的保底时间
k3~5抖动要乘几倍才安全
minDelay40~60ms再小就没法平滑了
maxDelay400~600ms再大通话体验就差到不可用了

WebRTC 的 NetEq 用的就是自适应策略，我们下一节细讲。

14.1.5 音频 vs 视频 Jitter Buffer 的差异 ​

维度音频（Audio）视频（Video）
帧大小固定（如 20ms Opus 帧）可变（I 帧大、P 帧小）
解码依赖通常一帧独立解码强依赖前序帧（除非使用 SVC）
丢失表现用 PLC（Packet Loss Concealment）插值，听感稍闷画面花屏 / 卡顿
Buffer 策略追求最小延迟（NetEq 甚至做加速/减速播放）允许更大深度，重点保流畅
组装逻辑一包一帧，按序播放一帧可能分多包（FU-A / STAP-A），需要聚合
典型深度60~150ms200~500ms

注意：WebRTC 在统一框架里分别实现了 NetEq（音频）和 JitterBuffer（视频），它们的底层数据结构类似，但上层控制策略差异很大。14.2 节会重点讲视频侧的帧组装与自适应延迟。

14.1.6 小结 ​

你应该记住
抖动 ≠ 延迟抖动是延迟的不稳定性，关键在于相邻包的间隔变化
transit = arrival - timestamp接收端唯一可用的时间差指标
三大任务乱序重排、消除抖动、控制延迟
固定深度简单但僵化适合低抖动场景；生产环境通常用自适应
音频和视频策略不同音频怕延迟，视频怕花屏
