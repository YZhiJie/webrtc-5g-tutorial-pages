14.2 进阶应用：自适应缓冲与帧组装 ​

从"能播"到"播好"，还差三件硬功夫：把多包拼成完整的视频帧、处理 seq 号的环形回绕、在丢包时发出 NACK 并权衡等待时间。本节把这些工业级细节讲透。

14.2.1 帧组装：同一 timestamp 的 RTP 包聚合成一帧 ​

音频通常一包一帧，但视频一帧可能高达几百 KB，远超 MTU（1500 字节）。发送端会把一帧切成多包 RTP，接收端必须把它们拼回完整的帧。

怎么判断"一帧的边界"？

看 RTP 头里的 marker 位（M bit）：

seq=100  ts=360000  M=0  payload=... (FU-A start)
seq=101  ts=360000  M=0  payload=... (FU-A middle)
seq=102  ts=360000  M=1  payload=... (FU-A end)  ← M=1 表示这是该帧的最后一包
seq=103  ts=366000  M=1  payload=... (P 帧，一包一帧)

规则：相同 timestamp 的 RTP 包属于同一帧；其中 marker=1 的包是最后一包。如果一帧中间缺了某包，即使收到 marker=1，这帧也是不完整的，不能送去解码。

┌─────────────────────────────────────────────────────────────┐
│  接收到的包：                                                │
│    seq=100 ✓  seq=101 ✗(丢了)  seq=102 ✓                     │
│                                                             │
│  组装器状态：                                                │
│    frame(ts=360000) = [100, ?, 102]   ← 中间有洞            │
│                                                             │
│  结果：该帧不完整，要么等 seq=101 重传，要么整帧丢弃          │
└─────────────────────────────────────────────────────────────┘

14.2.2 乱序窗口：seq 号环形缓冲，处理回绕（wrap-around） ​

RTP seq 是 16 位无符号整数，范围 0~65535。当 seq 超过 65535 后会**回绕（wrap-around）**回到 0。简单的"按 seq 排序"逻辑在回绕点会崩溃。

正确的比较方式 ​

用模 2^16 的差值判断先后：

js
// 判断 a 是否"在 b 之后"（考虑回绕）
function isNewer(a, b) {
  return (a - b + 65536) % 65536 < 32768;
}

isNewer(5, 65535);   // true  → 5 比 65535 新（回绕后）
isNewer(65535, 5);   // false → 65535 比 5 旧

环形缓冲区结构 ​

WebRTC 视频 JitterBuffer 用环形缓冲（Ring Buffer） 存储包：

        head
         │
         ▼
  ┌───┬───┬───┬───┬───┬───┬───┬───┐
  │ 4 │ 5 │ 6 │ . │ . │ . │ . │ . │   capacity = 8
  └───┴───┴───┴───┴───┴───┴───┴───┘
         ▲
        tail
  • 插入：直接放到 (seq - head) % capacity 的位置
  • 扩容：如果新包的 seq 离 head 太远（超过 capacity），说明缓冲区不够，要扩容或丢弃旧帧

14.2.3 NACK 触发条件：丢包后等多久再 NACK？ ​

NACK（Negative Acknowledgment） 是接收端主动告诉发送端"我丢了 seq=X 的包，请重传"。

触发 NACK 的时机是艺术与工程的结合：

策略说明适用场景
立即 NACK一发现 seq 空洞就发 NACK低延迟场景，但可能误判乱序
延迟 NACK等 kMaxNackDelay（如 10~40ms）再发，先给乱序一个机会通用
批量 NACK收集一批丢失的 seq 再一起发，减少 NACK 风暴高丢包场景

WebRTC 的策略是延迟 + 批量：发现空洞后先等一小段时间，同时把多个丢失的 seq 打包成一个 RTCP NACK 报文发出去。

注意：NACK 不是免费的。频繁 NACK 会让发送端不断重传，加剧拥塞，形成"NACK 风暴"。因此要限制：同一 seq 的 NACK 最多重发 kMaxNackRetries（如 5 次），且重传请求间隔要有指数退避。

14.2.4 WebRTC 的 NetEq / JitterBuffer 设计要点 ​

WebRTC 把音频和视频拆成两套独立的缓冲系统，设计思路差异很大：

NetEq（音频）JitterBuffer（视频）
核心目标语音可懂度 + 最小延迟画面流畅度
单位语音帧（20ms Opus）视频帧（可变大小）
乱序窗口较小（几十包）较大（几百包，因为一个 I 帧可能占几十包）
丢包处理PLC 插值（用历史波形预测）请求关键帧 / 跳帧
加速机制加速播放（accelerate）或减速播放（preemptive expand）快播（fast forward）
自适应算法统计 IAT 的直方图，计算最优延迟统计 IAT 标准差，调整目标延迟

NetEq 最有特色的设计是变速播放（Time-Scale Modification）：

  • 缓冲太满 → 轻微加速播放（人耳几乎听不出），把缓冲压回去
  • 缓冲太空 → 轻微减速播放，争取时间等新包

视频侧没有这么灵活，但可以通过跳帧（跳过非参考帧）来快速消化积压。

14.2.5 动态目标延迟：根据统计的 IAT 标准差调整 buffer 大小 ​

IAT（Inter-Arrival Time，包间到达间隔） 是衡量抖动最直接的指标。

IAT_i = arrival_i - arrival_{i-1}

如果网络完美，IAT 应该等于发送间隔（如 20ms）。现实中 IAT 会波动，波动越大，抖动越厉害。

用 IAT 的标准差来动态调整目标延迟：

js
// 简化版自适应算法
class AdaptiveJitterEstimator {
  constructor() {
    this.iatMean = 0;      // IAT 平均值
    this.iatStdDev = 0;    // IAT 标准差
    this.alpha = 0.05;     // 滑动平均系数
  }

  update(iat) {
    this.iatMean += this.alpha * (iat - this.iatMean);
    const diff = iat - this.iatMean;
    this.iatStdDev += this.alpha * (Math.abs(diff) - this.iatStdDev);
  }

  targetDelay(frameInterval) {
    // 目标延迟 = 帧间隔 + k × IAT 标准差
    const k = 3; // 覆盖 99.7% 的波动（假设正态分布）
    return frameInterval + k * this.iatStdDev;
  }
}

实际 WebRTC 用的是直方图法：记录最近 N 个包的 IAT 分布，找到能覆盖 95% 包的延迟值作为目标延迟。这比标准差更鲁棒，因为网络抖动往往不是正态分布。

14.2.6 kMaxWaitMs（最大等待时间）与播放延迟的折中 ​

即使等 NACK 重传，也不能无限等下去。kMaxWaitMs 定义了最多为一个丢包等多久：

┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   播放时刻        kMaxWaitMs                                 │
│      │              │                                       │
│      ▼              ▼                                       │
│  ────┼──────────────┼────────────────────► 时间             │
│      │              │                                       │
│      │         仍没等到 → 放弃该帧，                          │
│      │              发 FIR（请求关键帧）或跳到下一帧           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
场景kMaxWaitMs 建议后果
视频会议50~100ms偶尔跳帧，但延迟可控
直播200~500ms流畅优先，延迟可接受
云游戏30~60ms延迟敏感，宁可花屏

关键公式：

端到端延迟 ≈ 网络延迟 + Jitter Buffer 深度 + 解码时间 + 渲染时间
                     ↑
              你能控制的就是这一项

kMaxWaitMs 设得太长，Jitter Buffer 深度被动拉大，延迟失控；设得太短，又等不到重传，丢包率升高。

14.2.7 小结 ​

你应该记住
帧组装靠 timestamp + M bit同 timestamp 的包属于同一帧，M=1 是最后一包
seq 回绕用模 2^16 差值判断别直接用 a > b
NACK 要延迟 + 批量立即 NACK 容易误判，批量 NACK 减少风暴
NetEq 用变速播放音频侧独有的黑科技
目标延迟 = 帧间隔 + k × IAT 标准差自适应的核心公式
kMaxWaitMs 是延迟与流畅的开关视频会议调小，直播调大
