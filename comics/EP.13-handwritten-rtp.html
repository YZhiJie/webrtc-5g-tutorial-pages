EP.13 给每个 UDP 包编上号 ​

对应正文：模块十三 · 手写 RTP/RTCP 动手演示：手写 RTP 打包解包与统计

剧情回顾 ​

格场景
① 困境标签君用 UDP 直发媒体流，接收端包乱序 + 丢包，画面花屏、声音跳帧——UDP 不保证顺序、不保证到达。
② 揭秘码叔摊开 RTP 12 字节固定头：V/P/X/CC/M/PT/sequence/timestamp/SSRC。sequence 管顺序和丢包检测，timestamp 管播放时机和音画同步，分工明确。
③ 实证像素酱用 Node.js 给每帧 opus 手写 12 字节头（0x80 + PT + seq + ts + SSRC），打印 hex 验证；再手写 RTCP RR，统计丢包率和 jitter。
④ 结案码叔一句话总结：seq 管顺序、ts 管时机、RTCP 管反馈。坑点三条：seq 回绕比较、timestamp 用采样时钟不是墙钟、RTCP 复合包最小 28 字节。

知识点拆解 ​

① 为什么 UDP 需要 RTP ​

UDP 只提供"尽力投递"：不保证顺序、不保证到达、不保证不重。对实时音视频来说，这三个缺陷恰好都是致命的：

  • 乱序：解码器按 GOP 依赖关系解码，I 帧还没到就先收到 P 帧 → 花屏；
  • 丢包：H.264 的 P 帧丢失 → 后续所有依赖它的帧都解不出 → 直到下一个 IDR 帧才能恢复；
  • 无时间戳：接收端不知道该按什么节奏播放、怎么对齐音轨和画轨。

RTP（Real-time Transport Protocol，RFC 3550）就是盖在 UDP 之上的一层薄包头——只解决"编号 + 时机"，不做重传、不做拥塞控制（那是 RTCP 和 GCC 的事）。

V2版本，固定 2（即 0x80）

③ seq 和 timestamp 的分工 ​

字段解决什么怎么用
sequence丢包检测 + 重排序收到 seq = expected + k（k>1）→ 中间 k-1 个包丢了；JitterBuffer 按 seq 重新排队
timestamp播放时机 + 音画同步视频 90kHz 时钟：相邻帧差 3000（30fps）；音频 opus 48kHz：20ms 帧差 960

关键认知：timestamp 不是"发送时间"，而是"这帧数据的采样时刻"。编码排队、网络抖动都不影响它——它只反映源端节奏。

④ RTCP：RTP 的伴生反馈协议 ​

RTP 跑媒体，RTCP 跑统计。常用包型：

PT名称作用
200SR（Sender Report）发送端：发了多少包、多少字节、NTP/ RTP 时钟对照
201RR（Receiver Report）接收端：丢包率、jitter、最高收到的 seq、上次 SR 时间
202SDES源描述（CNAME 必须带）
205RTPFB传输层反馈（NACK / PLI / FIR）
206PSFB载荷反馈（REMB / TWCC）

复合包规则：RTCP 必须复合发送，且最小 28 字节——SR/RR（24 字节头 + report block）+ SDES CNAME（4 字节起）。如果单独发一个 RR，很多中间盒 / SFU 会直接丢包。

坑点清单（FAQ） ​

  • Q：seq 回绕怎么处理？ uint16 最大 65535，继续 +1 就回到 0。不要直接比大小，用差值比较：(a - b) & 0xFFFF，结果小于 32768 认为 a 更新。同样 expected_seq 也别用 +1，用 (expected_seq + 1) & 0xFFFF。
  • Q：timestamp 初始值可以从 0 开始吗？ 规范要求随机起点，防止嗅探者通过 seq/ts 推断会话内容。SSRC 同理必须随机生成，且会话内唯一。
  • Q：视频 90kHz、音频 48kHz，是怎么定的？ 视频 90kHz 是 MPEG 体系的传统（能整除 24/25/30/60fps）；opus 用 48kHz 是因为它的采样率就是 48kHz。两个流的 timestamp 不能直接对比，要靠 RTCP SR 里的 NTP↔RTP 时钟对照表来做音画同步。
  • Q：丢包率怎么算？ RTCP RR 里的 fraction lost 是 8 bit 定点小数（Q8），256 = 100%；cumulative lost 是 24 bit 有符号累计数。自己实现时按 (expected - received) / expected 在间隔内算。
  • Q：RTP 包最大能多大？ 受 MTU 限制，UDP payload 建议 ≤ 1200 字节——再大就容易被 IP 层分片，丢一个分片整包作废。视频一帧往往要拆几十个 RTP 包，靠 M bit 标记帧结束。
  • Q：PT=96 是固定的吗？ 96~127 是动态范围，必须在 SDP 里用 a=rtpmap 显式绑定。Chrome 默认视频 VP8 是 96、opus 是 111，但对端可能不一样，写 SFU 时千万别硬编码。

自测 3 题（含答案） ​

  1. RTP 固定头有哪 5 个核心字段？其中负责"丢包检测"和"播放时机"的分别是哪一个？
  2. 收到 seq = 5 的包后，下一个期望的 seq 是多少？如果连续收到 seq = 5、8、6，说明发生了什么？（用回绕安全的方式写伪代码）
  3. 为什么 RTCP RR 单独发会被中间盒丢掉？复合包的最小构成是什么？
答案

  1. 5 个核心字段：V / M / PT / sequence / timestamp / SSRC（严格说是 6 个，V 通常不算字段因为固定为 2）。丢包检测 = sequence number（每包 +1，跳号即丢）；播放时机 = timestamp（采样时刻，用媒体时钟）。

  2. 下一个期望 seq = 6（回绕安全写法：(5 + 1) & 0xFFFF）。连续收到 5、8、6 说明：

    • seq=6 比 seq=8 晚到 → 乱序（seq=6 走了不同路径）；
    • seq=7 没出现 → 要么丢了，要么还在路上，需要 JitterBuffer 等几个毫秒再判。

    回绕安全的比较伪代码：

    js
    const NEWER = (a, b) => ((a - b) & 0xFFFF) < 32768 && a !== b
// 收到 65535 后又收到 0：((0 - 65535) & 0xFFFF) = 1 < 32768 → 0 更新

  3. 因为 RFC 3550 规定 RTCP 必须以复合包（Compound Packet）形式发送，第一个包必须是 SR 或 RR，且必须紧跟一个 SDES CNAME——总长度最小 28 字节（RR 24B + SDES 4B）。中间盒 / SFU 会校验这个结构，单独一个裸 RR（24B）不满足最小长度 + 缺 CNAME，会被当成畸形包丢弃。
